Deep dive: the use-after-free, step by step

First, two terms you'll see throughout
ZendMM (Zend Memory Manager)
PHP's own memory manager, built on top of the operating system's memory. Instead of asking the OS for memory every time, PHP asks ZendMM, which hands out small blocks and keeps a ledger of who owns what. It is a middle man between your PHP script and the computer's raw memory, tracking every allocation so it can be freed cleanly at the end of the request.
zend_object
The C structure PHP uses to represent an object in memory. Every object you create in PHP code is really a zend_object behind the scenes: a fixed-size block of bytes holding
  1. its type,
  2. its handlers, which include a pointer to its own destructor , the function that runs when the object is cleaned up
  3. its data.
This attack works by faking one of these structures so PHP runs the attacker’s chosen “destructor”.

The two ledgers

To see how the trick works, you need to know that two separate systems are keeping track of the same memory, and they don't talk to each other.

The OS ledger tracks physical RAM pages. When PHP asks for memory, the OS hands over a page and marks it “in use” and when PHP frees it, the OS marks it “free”. The OS has no idea what a zend_object is. It only tracks raw blocks.

The ZendMM ledger is PHP's own accountant, one level up. When the engine calls emalloc(), ZendMM records a row (“Block X is owned by this variable”) and also gets the block from the OS underneath. At the end of a request ZendMM walks its ledger and frees everything.

Everything lives in RAM, not on disk. An HTTP request arrives over the network, the kernel drops its bytes into a buffer in RAM, and PHP's parser reads from that buffer and writes the parsed data into a heap block, also in RAM. Nothing touches the disk until PHP explicitly writes a file. So Request A's object and Request B's payload are both just regions of the worker's memory, which is why one can land exactly where the other used to be.

PART 1: THE CRASH

OOMUAF created The OOM & the dangling pointer

In a normal request, PHP tracks variables using the Zend Memory Manager (ZendMM).

The attacker passes request A with the flag to track upload progress. So when Request A uploads a file, ZendMM allocates a 256-byte zend_object (Block X) to track the progress and stores the pointer in the $_SESSION array. Everything is consistent: the ledger and the session pointer agree on who owns Block X.

The attacker sends a massive payload, causing PHP to hit its memory_limit cause OOM fault. PHP panics and calls longjmp().

longjmp() is a violent C function: it jumps the execution pointer directly to the shutdown phase, completely skipping the normal variable teardown. Because teardown is skipped, ZendMM's ledger is never updated and the pointer inside $_SESSION is never deleted. The OS marks Block X as “free” to save memory, but PHP still thinks it owns it.

PART 2: THE REUSE

UAF reclaim Why Request B's bytes get in

Both requests are parsed into a temporary buffer the same way. The difference is the flag: PHP only builds a tracked zend_object when it reads the session.upload_progress flag, which Request A had and already did. Request B is sent without that flag, so PHP never builds a second tracked object for the same block.

Request B is also crafted so its payload is 256 bytes, exactly the size of the Block X that was just freed. If it arrives soon enough after the crash, the OS hands that same freed block back to Request B. Keep in mind that PHP still believes this block is holding upload progress, because nothing ever cleared the $_SESSION pointer.

So Request B's body is written into that memory, and the attacker's data now sits in the exact slot $_SESSION still points at, with no ownership check and no double-free to stop it.

Request A (has the flag)
parsed into a temporary buffer → upload_progress flag read → PHP builds a tracked zend_object → Block X allocated
Request B (no flag)
parsed into a temporary buffer → no flag, nothing to build → bytes land in freed memory → Block X overwritten, no crash
Both requests are parsed into a temporary buffer the same way. The fork is the upload_progress flag: when PHP reads it in Request A, it builds the tracked object (Block X). Request B has no flag, so PHP never builds a new tracked object; its bytes just overwrite the freed block, with no ownership check and no double-free.

PART 4: THE ADDRESS

Finding where system() lives in memory

The handler in the fake object has to point at the exact memory address of system(). That is hard, because of ASLR (Address Space Layout Randomisation): on every run the operating system loads libraries at a different random base address, so system() is never at a fixed, known location. The attacker has to work out where it landed this time.

In practice there are a few reliable ways to recover that address:

1
Leak it from the process itself An exposed phpinfo() page, a verbose stack trace, or a separate memory-disclosure bug prints real pointers. From one leaked address the attacker computes the library's base, then adds the known fixed offset of system() within that library.
2
Compute it from the libc version If the server's libc build is known (from headers, an error, or fingerprinting), the offset of system() inside that exact libc is a constant. Leaked base address plus that constant gives the real address.
3
Brute-force a weak layout On 32-bit systems, or where ASLR entropy is low or the worker keeps restarting at the same base, the attacker can simply try many candidate addresses until one works. Slow and noisy, but sometimes enough.
The common thread: leak one real address, then turn it into the address of system() using a known, fixed offset.

Without one of these, the handler points at the wrong place and the process just crashes instead of running a command. Recovering the address is what turns a crash into reliable code execution.

PART 5: THE EXECUTION

UAF triggered Shutdown and the fake destructor

The PHP worker process runs php_request_shutdown() to clean up sockets after each request.

The shutdown routine walks the $_SESSION array, reads the dangling pointer that was never deleted, and follows it to Block X. It sees the attacker's fake object, reads the “handler” pointer, and calls it. This is where the UAF is triggered .

Remote code execution php_request_shutdown() → follows pointer → calls 0x7FFD5C3A → system("id")
PART 6: THE MEMORY

Why doesn't php_request_shutdown() remove the memory ZendMM entry?

If shutdown is the thing that normally frees everything, so why doesn't it notice that Block X was already freed and delete the stale pointer?

Because shutdown does not re-check ownership. It simply walks $_SESSION, trusts whatever pointer it finds, and calls the handler. The normal teardown that would have removed the pointer when Block X was freed never ran, because the crash used longjmp() to jump straight past it. So from shutdown's point of view the pointer looks perfectly valid, and it follows it into memory that has since been reused.

This raises a question: if Request A was aborted, how does shutdown still run? The answer is that aborting the request does not kill the process doing the work. PHP runs inside a worker process that handles many requests one after another. A fatal error ends the current script (request A) but the worker still runs and performs the worker's shutdown routine.

How a fix breaks the chain

Modern PHP (8.2.35+) replaces the violent longjmp() with a “soft OOM” mechanism, letting the engine gracefully unwind the stack and safely reset the ZendMM ledger and $_SESSION array, so the dangling pointer never exists in the first place.
