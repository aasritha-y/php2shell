PHP2Shell: The Stale Global State Chain

The idea: trigger a fatal error while PHP is unserializing session data, so the engine skips its cleanup. The worker survives, but its internal state is left pointing at freed memory.

ATTACKER Send Request A (The Poison)

The attacker starts a session that holds serialized data and crafts it so PHP has to unserialize it. To do that, PHP allocates a 512-byte var_hash block as a buffer and keeps a pointer to it so it can find the block again while decoding.

PHP saves session data to disk as serialized text: a flat string that encodes each value's type and contents. When that session is loaded again, PHP has to unserialize it, rebuilding the string back into real PHP values and objects. The unserializer runs automatically whenever a session with serialized data is loaded, and it is this step that builds the var_hash block, which is why the attack starts here.

ENGINE Fatal Error → emergency bailout

The attacker builds Request A so that it hits a fatal error while PHP is still unserializing. On a fatal error PHP jumps straight to shutdown, skipping the normal cleanup.

So the step that would have cleared the pointer to the var_hash block never runs, and that pointer is left behind.

3

ENGINE Block freed, but EG survives

The Request A exists due to the fatal error. ZendMM wipes its ledger and frees the var_hash block. But because the reset was skipped, the worker's global EG struct still holds the address of the var_hash block.

The EG is global struct unique to a PHP worker. Recall that a PHP worker is a single threaded process that executes requests one after another. The PHP worker is now poisoned.

ATTACKER Send Request B (Reclaim the Block)

The attacker sends Request B with a payload of exactly 512 bytes. The timing request B is set such that it is processed immediately after releasing var_hash block.

Thus the block is handed straight to Request B and the attacker's fake var_hash data is written directly into the block now.

THE CORE BUG When the fatal error exits, it clears ZendMM's ledger but not the global EG struct. ZendMM now thinks the block is free while EG still points at it.

This is a separate bug from CVE-2026-109618 (which leaves a stale $_SESSION pointer instead), but both land in the same place: a use-after-free (UAF) .

ENGINE Request C Arrives (The Trigger)

A normal user (or the attacker) sends Request C, which lands on the same poisoned worker. PHP calls the unserializer again, and it checks EG(unserialize).level before starting fresh. That level is a guard that is supposed to be 0 at the start of a new decode, but Request A left it stuck at 1.

Seeing 1, the unserializer believes a decode is already in progress, so instead of allocating a new struct it reuses the existing var_hash block, which is now filled with the attacker's fake data.

6

ENGINE The stale pointer executes

The engine blindly follows the stale EG pointer to the var_hash block. It reads the var_hash placed by Request B and executes it. Request C is hijacked before it runs its own code.

Deep dive: The architecture of EG & var_hash

The C Structs involved
EG (Executor Globals)
A massive global C struct created once when the worker starts. It persists across requests. It is not tracked by ZendMM.
var_hash (HashTable)
A 512-byte C struct allocated during unserialization to track decoded objects and prevent infinite recursion.
PART 1: THE STRUCT DEFINITIONS

The two structs this attack hijacks

Here is a simplified, real-world representation of what the executor_globals struct looks like in the PHP source code (Zend/zend_globals.h):

struct _zend_executor_globals (EG)
struct _zend_executor_globals {
  // ... other fields ...
  HashTable *symbol_table;
  zend_execute_data *current_execute_data;

  // THE SERIALIZATION STATE (The 109619 Bug)
  struct {
    int level;              // 0 = idle, 1 = decoding
    HashTable *var_hash;    // Pointer to the 512-byte block
  } unserialize;
};
When you see EG(unserialize).var_hash, it is a macro accessing the var_hash pointer inside the unserialize struct inside the global executor_globals.

And here is what the var_hash struct (a HashTable) looks like:

struct _zend_hash_table (var_hash)
struct _zend_hash_table {
  uint32_t nTableSize;      // Size of the table (512 bytes)
  uint32_t nNumOfElements;  // How many objects tracked
  Bucket *pListHead;        // Pointer to first element
  Bucket *pListTail;        // Pointer to last element
  // ... internal memory management pointers ...
};
This is the 512-byte block. The attacker overwrites pListHead to point to a fake object with a destructor.
PART 2: THE EXPLOIT FLOW

From a fatal error to a hijacked destructor

Normal operation: During a session decode, PHP creates the var_hash HashTable. It sets EG to point to this var_hash table and sets EG(unserialize).level = 1 to mark that a decode is in progress. Usually the PHP_VAR_UNSERIALIZE_DESTROY frees the block and resets EG back to NULL and 0.

The poison (Request A): The attacker triggers a fatal error mid-decode. zend_bailout() jumps straight to shutdown and skips PHP_VAR_UNSERIALIZE_DESTROY. ZendMM still frees the 512-byte block, but EG(unserialize).level stays at 1 and EG(unserialize).var_hash still points at the freed block.

The reclaim (Request B): Request B is crafted so its allocation is exactly 512 bytes, the same size as the var_hash block that was just freed. If it arrives soon enough after the crash, ZendMM hands that same freed block back to Request B. Keep in mind that EG(unserialize).var_hash still points at this block, because nothing ever cleared it. The attacker doesn't send random bytes. They write a binary payload crafted to look exactly like a real HashTable, with its pListHead pointing to a fake object whose destructor points to system().

The Trigger (Request C): The attack makes Request C lands on the same poisoned worker (can do this by sending multiple requests) and PHP calls the unserializer again.

It checks EG(unserialize).level before starting fresh. That level is a guard that is supposed to be 0 at the start of a new decode, but Request A left it stuck at 1.

Seeing 1, the unserializer believes a decode is already in progress, so instead of allocating a new struct it reuses the existing block by following the stale EG(unserialize).var_hash pointer, which now holds the attacker's fake HashTable, and executes the fake destructor.

How a fix breaks the chain

Modern PHP versions ensure that EG(unserialize).level and var_hash are explicitly reset at the very beginning of new request. Even if a previous request left the global state dirty, Request C will safely overwrite it before the parser tries to use it.
